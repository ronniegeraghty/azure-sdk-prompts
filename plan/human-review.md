The build verification concept should be reimplemented as a proper build grader that can be added as an evaluation criteria in config YAML (e.g., `kind: build`), not a hardcoded pipeline phase. Investigate how the existing grader framework (`internal/graders/`) can support a build grader that runs language-specific compile/syntax checks as part of the grading step.
- **Refactor `internal/config/` — split and generalize tool handling** — Package does too much: config loading, project discovery, plugin expansion, tool filtering, and skill installation. Should split into focused packages. More importantly, generalize tool handling: plugins are just a hyoka abstraction that gets flattened to skills + MCP configs before the SDK session. At the SDK level there are only three tool mechanisms: `SkillDirectories`, `MCPServers`, and `AvailableTools/ExcludedTools`. The acquisition layer (local vs remote fetch, caching, version tracking) should be shared across all tool types regardless of whether they were declared as skills, plugins, or MCP servers in the config. `plugins.go` should not be its own special path — it should use the same resolution as skills.
- **Isolate skills per-session more strictly** — Currently `SkillDirectories` points directly to resolved paths (cache, installed-plugins, local dirs). If a cached directory contains more skills than the config requested (e.g., `npx skills add microsoft/skills` pulls the whole repo), all skills in that directory get loaded. Should copy only the specific needed skills into a per-session temp directory for full isolation. The `NewIsolatedConfigDir()` pattern already exists for config isolation — extend the same approach to skills.
- **Investigate remote MCP server support** — Currently only `"type": "local"` MCP servers are supported (command + args to spawn a process). The Copilot SDK's `MCPServerConfig` supports remote MCP servers as well. Look into adding support for remote MCP servers in config YAML for scenarios where the MCP server runs on a different host.
- **Extract tool handling into a dedicated `internal/tool` package** — Centralize all tool resolution, acquisition, caching, and session injection into one package. Should handle skills, MCP servers, and plugins uniformly with shared patterns for: (1) local vs remote resolution, (2) caching in `~/.hyoka/cache/`, (3) version tracking, (4) per-session isolation — copying only config-declared tools into a temp dir, (5) validation that all tools from the config are present in the session and none are missing. This replaces the current scattered handling across `config/plugins.go`, `skills/fetcher.go`, `eval/copilot.go:buildSessionConfig`, and `cmd/helpers.go:resolveConfigSkillDirs`. This new package should be a sub-package of `config/` (i.e., `config/tool/`) since tools are fundamentally part of the config system.
- **Harden criteria system end-to-end** — Three things to verify and fix: (1) Attribute-matched criteria from `criteria/` YAML files are properly picked up when a relevant prompt is evaluated (language, service, etc. matching works). (2) The matching logic works for criteria types beyond `prompt` graders (e.g., file, behavior, program graders). (3) Prompt-specific eval criteria from `## Evaluation Criteria` sections are retrieved and properly merged with attribute-matched criteria. Consider restructuring: make graders a sub-package of criteria (`criteria/graders/`) with the different grader types and their handling. The agent review panel would be one type of grader alongside file, behavior, program, and build graders.
- **Add hierarchical `when` support to criteria files** — Currently criteria files only support a top-level `when` for the whole file. Should support: (1) top-level `when` for the whole file (e.g., `language=python`), (2) `when` on groups of criteria within a file (e.g., `tag=code-gen`), (3) `when` on individual grader entries (e.g., `service=keyvault`). This allows a single `python.yaml` file to contain criteria that apply to all Python evals, plus specialized criteria for specific services/tags. Also need to document clearly how criteria from YAML files merge with criteria from prompt `## Evaluation Criteria` sections.
- **Move pairwise expansion into `Engine.Run()`** — Currently done in `cmd/run.go` before calling the engine. Should be inside `Engine.Run()` alongside the other prompt × config expansion logic so all task expansion is in one place.
- **Rename `CopilotEvaluator.Evaluate()` to reflect its role** — It only does the generation/session work, not evaluation. Name should denote it's the Copilot session that attempts what the prompt asks — not "generator" (hyoka isn't just for code generation) and not "evaluator" (the eval is the whole pipeline). Something like `CopilotSession.Execute()` or `PromptRunner.Run()`.
- **Unify criteria and graders into one evaluation system** — Currently criteria (attribute-matched + prompt-specific) and graders (behavior, file, program, prompt) are separate systems. Should be one unified grading pipeline where the AI review panel is just one grader type alongside file, behavior, program, and build graders. Criteria checking should be its own explicit pipeline step, not inline during the review phase.
- **Verify tools loaded after session creation using SDK events** — The Copilot SDK emits `session.mcp_servers_loaded`, `session.mcp_server_status_changed`, and `session.extensions_loaded` events. After `CreateSession()`, listen for these events to verify all requested tools/skills/MCP servers loaded successfully. Fail fast if any are missing or failed to start rather than discovering mid-eval.
- **Build timeline from events during report generation, not during eval** — Currently both raw `SessionEvents` and processed `ActionTimeline` are built during the eval and stored on `EvalResult`. More efficient to just capture raw events during eval and build the timeline later during report generation — reduces eval-time processing and keeps the eval focused on generation.
- **Implement dual-mode AI prompt grader evaluation** — Add support for two modes: (1) single review agent that checks all AI prompt grader criteria at once (current approach, faster), (2) one agent session per criterion for improved stability (each criterion evaluated independently — one failing doesn't affect others). Allow users to select the mode via config or CLI flag. Compare results between modes to assess reliability.
